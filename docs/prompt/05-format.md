# 05 · 把输出格式钉死

<div class="ab-def">

"要求"那一格里最值钱的部分，是**输出长什么样**。形容词（简洁、专业、条理清楚）不算约束，只有**结构**才算：分几块、每块叫什么、每块里放什么。

</div>

## 从形容词到结构，一张对照表

| 你想要的 | 别这么说 | 这么说 |
| --- | --- | --- |
| 短 | 简洁一点 | 总共不超过五条，每条一行 |
| 长 | 详细展开 | 每个要点下面各给一个具体例子和一个反例 |
| 有条理 | 结构清晰 | 分三块，标题分别是「结论」「待办」「遗留」 |
| 专业 | 写得专业一点 | 每个结论后面跟一个来自材料的数据或原话 |
| 能直接用 | 可执行一点 | 每条待办写成"谁 + 在什么时间前 + 做什么" |
| 不啰嗦 | 别废话 | 不要开场白、不要复述我的问题、不要结尾总结 |

规律：**把形容词翻译成"可以数出来 / 可以查出来"的东西**。

## 最好用的一招：给模板让它填空

比描述结构更硬的，是直接把模子给它：

```text
严格按下面的模板输出，方括号里换成实际内容，模板本身的文字和顺序不要改：

## [项目名]｜[会议类型] 纪要

**日期**：[YYYY-MM-DD，原文没写就填"待确认"]
**参会**：[列出，用顿号分隔]

### 一、已定事项
1. [一句话一条，动词开头]

### 二、待办
| 事项 | 负责人 | 截止 |
| --- | --- | --- |
| [事项] | [人名或"待确认"] | [时间或"待确认"] |

### 三、遗留问题
1. [一句话一条]
```

方括号里顺手写上填写说明（"原文没写就填待确认"），比在别处另写一条规则更容易被遵守——**说明就在它要填的地方**。

::: tip 模板要不要留弹性
两种写法，按需要选：

- **严格**："严格按下面的模板输出，不要增删章节。"——适合要进系统、要归档、要跟别的文档对齐的场景。
- **有弹性**："下面是默认结构，可以按实际内容增减章节，但一、二、三这三块必须有。"——适合内容差异大的场景。

别含糊其辞。你不说，它每次自己决定，你就得到了不稳定。
:::

## 要给程序用：JSON 和结构化输出

输出如果要被代码接走，就别让它写散文。

```text
只输出一个 JSON 对象，不要有任何解释文字，不要用 Markdown 代码块包裹。

结构如下：
{
  "客户": "字符串，材料里的客户名，没有则为 null",
  "已定事项": ["字符串数组，每条一句话"],
  "待办": [
    {"事项": "字符串", "负责人": "字符串或 null", "截止": "YYYY-MM-DD 或 null"}
  ],
  "待确认": ["字符串数组"]
}

规则：材料里没有的信息一律用 null，不要填空字符串，不要猜。
```

三个要点：

1. **字段说明写在结构里**，别另起一段解释。
2. **明确"没有"该填什么**（`null` 还是 `""` 还是 `"待确认"`）——不说的话它三种都会用。
3. **明确"只输出 JSON"**，否则它爱在前面加一句"好的，这是您要的 JSON："。

::: tip 更硬的做法
很多平台和 API 提供「Structured Output」/ JSON 模式，可以直接给一份 JSON Schema，由系统保证输出合法。**能用这个就别靠提示词硬求**——提示词只能提高概率，系统级约束才是保证。见[术语表](../reference/glossary)。
:::

## 长度：别用字数

[03 · Token](../start/03-token) 讲过原因——它眼里没有"字"这个单位。可用的长度控制：

| 想要 | 怎么写 |
| --- | --- |
| 很短 | "一句话"、"不超过三条，每条一行" |
| 中等 | "三段，每段三到四句" |
| 长 | "每个要点展开成一小节，含一个例子" |
| 卡死上限 | "总长度控制在一屏以内（约 15 行）" |

想更准，就用**结构 + 数量**双约束："五条，每条一行，每行不超过一句话。"

## 三条通用的"减噪"规则

这三句几乎可以加到任何提示词里：

```text
- 不要开场白，不要复述我的问题，直接给结果。
- 不要在结尾加总结、建议或"希望对您有帮助"。
- 除非我要求，不要解释你的思路。
```

它们省 Token，也省你的眼睛。加进 [System Prompt](../start/07-system-prompt) 就一劳永逸了。

## 一个容易被忽略的坑：Markdown

模型默认爱用 Markdown——加粗、列表、表格、标题。这在支持渲染的地方很好看，**但你要是把结果粘到微信、粘到邮件、粘到不支持 Markdown 的系统里，满屏的 `**` 和 `|` 就成了噪音**。

要纯文本就明说：

```text
输出纯文本，不要使用 Markdown：不要用 * 加粗、不要用 # 标题、不要用表格。
分点用「1. 2. 3.」，层级用缩进。
```

反过来，要表格就明确说"用 Markdown 表格"，否则它可能给你一段带对齐空格的文本。

<div class="ab-do">

给你手上最常用的那条提示词做三件事：

1. 找出所有形容词式的要求，按上面那张对照表换成结构约束；
2. 如果输出结构固定，直接写成模板让它填空；
3. 加上那三条"减噪"规则。

改完再跑五次，看是不是五次都长得差不多。

</div>
