# Agent 篇 · 放手，但别撒手

[Workflow 篇](../workflow/)的结论是：**能把步骤写下来，就写下来。**

这一篇处理的是剩下那种情况——**你写不下来**。

> "把这个 bug 查出来" —— 可能三步，可能三十步，取决于查到什么。
> "找齐这五家竞品的定价" —— 有的官网首页就有，有的要翻到第三层，有的得看 PDF。
> "这份数据里有什么值得注意的" —— 你事先不知道有什么，所以也不知道要看几轮。

这类活的共同点是：**下一步干什么，取决于上一步看到了什么。** 你没法事先画出流程图，因为图的形状是跑起来才知道的。

这时候你需要的是一个 Agent：**你给目标，它自己拆步骤、执行、检查、再修正。**

## 先把上一篇的结论重申一遍

::: warning 这一篇不是给你换个更高级的做法
**Agent 不是 Workflow 的升级版。** 它是拿三样东西——可预测性、可调试性、成本上限——去换一样东西：能处理你没预想到的情况。

这笔交易只在**你确实预想不到**的时候才划算。

所以这一篇的每一章，本质都在回答同一个问题：**交出去之后，怎么把那三样东西尽量捞回来一点。**
:::

而且要记住上一篇那句收口——**Agent 更常见的用法是局部**：整条线还是 Workflow，只有拿不准的那一步放一个 Agent。这一篇讲的所有东西，对"那一步"同样成立。

## 一句话，先给你

> **能力决定它能跑多远，边界决定你敢不敢让它跑。**

绝大多数 Agent 项目死掉，不是因为模型不够聪明，是因为**没人敢用**——它能干，但没人知道它会干出什么，于是每次都得有人全程盯着。全程盯着的 Agent，还不如一条 Workflow。

所以这一篇有一半篇幅在讲边界、上限、留痕、验收。**不是保守，是让它真的能被放出去用。**
