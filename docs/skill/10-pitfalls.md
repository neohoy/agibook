# 10 · 十个坑

按"踩的人多少"排序。前三个占了新手问题的一大半。

## 1. description 只写了"做什么"，没写"什么时候用"

**症状**：Skill 从来不触发，你每次都得手动说"用那个纪要的规矩"。

**原因**：系统判断要不要用它，看的就是这一句。少了"什么时候用"，它没有匹配依据。

**修法**：把你和同事**真会说的那几句话**里的关键词全塞进去。测法见 [04 章](./04-description)那个自测。

## 2. 把"这一次的材料"写进了 Skill

**症状**：做 B 项目的纪要，输出里冒出 A 项目的客户名。

**原因**：你直接把调好的那条提示词整个复制进去了，里面还留着"明远地产""会员小程序改版"。

**修法**：Skill 里只留**每次都一样**的东西。判断方法在 [05 章](./05-write-one)第 1 步：两支笔圈一遍。

## 3. 正文里科普常识

**症状**：正文写了三页，效果还不如你原来那条提示词。

**原因**：一半篇幅在解释"会议纪要是什么""为什么要写待办"。它知道。这些字挤掉了真正有用的内容。

**修法**：只写"**我们这儿和别人不一样**"的部分。写完自问每一段："这句删掉会怎样？"没影响就删。

## 4. 只有禁止，没有出路

**症状**：写了"不要编造人名"，它还是编。

**原因**：跟[提示词篇 06 章](../prompt/06-constraints)是同一个问题——你堵死了一条路，没给新路。

**修法**：每个"不要"后面配一个动作。"不要补全人名" → "人名沿用原文称呼；原文没提到的人，写「待确认」"。

## 5. 一个 Skill 干两件事

**症状**：你的"文档助手"既管纪要又管周报，结果两边都触发得不准，写周报时套上了纪要的三块结构。

**原因**：description 必须同时描述两类活，就只能写得很宽，宽了就误触发。

**修法**：**一个 Skill 一件事。** 判断标准：你能不能用一句话说清"什么时候用这个"。

## 6. 规矩堆到二十条

**症状**：前几条生效，中间几条时灵时不灵。

**原因**：长列表里靠中间的最容易被忽略——跟[长材料读漏](../start/04-context)是同一个机制。

**修法**：正文里留最重要的五到八条；剩下的要么删，要么移到附件，要么想想是不是该拆成两个 Skill。

## 7. 附件套附件

**症状**：Skill 里有一份很详细的规范文档，但它明显没读全。

**原因**：`SKILL.md` → `A.md` → `B.md` 这种嵌套引用，它可能只扫一眼 B 就走了，拿到的是残缺信息。

**修法**：**所有附件都从主文件直接指过去，只能一层深。** 超过一百行的附件，开头加一份小目录。

## 8. 写了会过期的内容

**症状**：半年后 Skill 里还写着"7 月之前用旧模板"。

**修法**：只写当前的做法。旧的收进折叠区，或者删掉。见 [08 章](./08-iterate)。

## 9. 在同一个对话里"写完顺便测一下"

**症状**：自己测都过，一到真实使用就不行。

**原因**：刚写完的内容还在[上下文](../start/04-context)里，它当然照做——这是自己出题自己判卷。

**修法**：**开一个干净的新对话**，只装 Skill，用一句平常会说的话去触发。这才是真实情况。

## 10. 装来路不明的 Skill

**症状**：AI 做了你没预期的事。

**原因**：Skill 里的文字就是给 AI 的指令。当 AI 手上有文件读写、执行命令、连外部系统这些能力时，**一个不怀好意的 Skill 能指挥它做很多事**。

**修法**：只用自己写的，或者来源可信的。第三方的 Skill，装之前把**所有文件**（正文、附件、脚本）从头读一遍，看有没有跟宣称用途对不上的操作。

**把它当成在自己电脑上装软件来对待，而不是复制一段文本。**

## 快速自检

发布一个新 Skill 之前，对着这张表过一遍：

- [ ] description 里有"做什么" **和** "什么时候用"
- [ ] description 覆盖了至少三种不同的说法
- [ ] （装了三个以上 Skill 的话）有排除条款
- [ ] 正文里没有具体的客户名 / 项目名 / 日期
- [ ] 正文里没有对常识的解释
- [ ] 每条"不要"后面都跟了"那就……"
- [ ] 规矩不超过八条
- [ ] 附件引用只有一层深
- [ ] 有至少一组示例，且包含一个边界情况
- [ ] 有一份可勾选的检查清单
- [ ] 在**新开的干净对话**里跑过三个用例
- [ ] 三个用例包括"不该触发"那一个

## 这一篇的收口

十章可以压成三句：

> **description 决定它会不会被用上**——一半的功夫花这儿。
>
> **正文只写"我们这儿不一样"的部分**——常识一个字都别写。
>
> **先测出它会错在哪，再写刚好能修好的内容**——不要凭想象写说明书。

## 然后呢

你现在走完了三步：

| | 你会了什么 |
| --- | --- |
| [入门篇](../start/) | 知道它是什么、为什么会忘会编、怎么把一件事说清楚 |
| [提示词篇](../prompt/) | 让一条提示词稳定、可验收、能交接 |
| **Skill 篇** | 把跑通的东西打包，一次写好、反复触发、团队共用 |

下一格是 [Workflow](../workflow/)——真实的活很少只有一步，你需要把几个已经跑通的步骤串成一条流水线：每步能验收、错了知道停在哪。**你现在写的每一个 Skill，都是那条流水线上的一个节点。**

不过别急着去。先把手上那一个 Skill 用满两周，观察它在哪儿不听话——**那两周学到的东西，比再读十章都多。**
