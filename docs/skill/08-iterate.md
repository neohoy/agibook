# 08 · 迭代与维护

Skill 发出去只是开始。这一章讲三件事：怎么改、什么时候拆、怎么在团队里活下来。

## 让 AI 帮你写 Skill（正确姿势）

模型很懂 Skill 该怎么写——**它自己就是读这个的**。但"帮我写个 Skill"这种要法效果一般，正确的做法是**用两个对话**：

```text
对话 A（教练）：帮你设计和改 Skill
对话 B（学生）：装着这个 Skill，干真实的活
```

流程：

**1. 先在对话 A 里，用普通提示词把一件事做对。**

一来一回的过程中，你会自然地补充背景、纠正方向、说明偏好。**注意你重复说了哪些话**——那些就是该进 Skill 的东西。

**2. 让对话 A 把刚才这一段打包。**

```text
把我们刚才整理纪要的这套做法，写成一个 Skill。
要包含：输出结构、人名不补全的规则、拿不准标「待确认」的规则、
以及跑题内容怎么归类。
description 要覆盖这几种说法：整理纪要、理一下会议记录、提取会议待办。
```

**3. 让它删掉废话。**

```text
把解释性的内容全删掉——不要解释什么是会议纪要、不要解释为什么要写待办。
只保留"我们这儿和别人不一样"的部分。
```

这一步很重要，AI 写 Skill 最大的毛病就是**太啰嗦**：它会认真给你科普一遍常识。

**4. 拿到对话 B 去用。** 装上 Skill，做真实的活，**观察它的行为**。

**5. 带着观察回到对话 A。**

```text
这是当前的 SKILL.md：【贴】

我用它处理一份记录时，它还是把"刘总监"补成了全名。
Skill 里明明写了"人名沿用原文称呼"。

分析：为什么这条没生效？给出最小的修改。
```

它可能会建议：把这条挪到更靠前的位置、语气改硬（"必须"而不是"尽量"）、或者在示例里加一个专门演示这一点的例子。

**6. 改完再测，重复。**

::: tip 为什么必须是两个对话
在同一个对话里"写完 Skill 顺便测一下"是无效的——**它刚写完，内容还在上下文里，当然做得对**。

必须开一个干净的对话，只装 Skill，才能测出真实效果。这跟"自己出题自己判卷"是同一个道理。
:::

## 三种典型的改法

观察到问题之后，按这个顺序试：

### 症状：从来不触发

**改 description。** 九成的情况都是这一条，见 [04 章](./04-description)。

具体做法：把你实际说的那句话，原样加进 description 的关键词里。

### 症状：触发了，但某条规矩总不生效

三个改法，从轻到重：

| 改法 | 怎么做 |
| --- | --- |
| **挪位置** | 把这条规矩从"规则"列表的中间挪到最前面，或者挪到流程步骤里 |
| **加硬度** | "尽量" → "必须"；"注意" → "不得" |
| **给例子** | 加一组 ❌/✅ 专门演示这一条。**这个最有效** |

例子最有效的原因在[提示词篇 03 章](../prompt/03-examples)：**它模仿的是形，比理解规则更可靠。**

### 症状：不该触发的时候触发了

在 description 里加排除条款，并指明该用哪个：

```yaml
description: ……仅用于会议类材料；整理个人工作流水用 weekly-report。
```

## 什么时候该拆

三个信号：

**信号 1：正文超过几百行。** 常见建议是控制在 500 行以内。超了就往附件拆。

**信号 2：一个 Skill 在处理两类不同的活。** 比如"文档助手"既管纪要又管周报——那就该是两个 Skill。**一个 Skill 一件事**，触发才准，维护才清楚。

**信号 3：不同分支之间基本没有重叠。** 三种会议类型的模板完全不同，就把模板拆进附件，主文件只留导航。

::: warning 反过来也要警惕：拆太碎
五个 Skill 各自只有十行，而且经常要一起用——那就该合成一个。

**判断标准：你能不能一句话说清"什么时候用这个"。** 说不清就是切得不对。
:::

## 别让 Skill 过期

Skill 会烂掉，主要有三种烂法：

### 一、写了会过期的内容

```text
❌ 2026 年 6 月之前用旧模板，之后用新模板。
```

三个月后没人记得这句话还在。正确做法是**只写当前的做法**，旧的收进一个折叠的"历史"小节，或者干脆删掉：

```markdown
## 当前模板
【新模板】

<details>
<summary>旧模板（2026-06 起停用）</summary>
【旧模板】
</details>
```

### 二、术语前后不一致

同一个东西，一会儿叫"待办"，一会儿叫"任务"，一会儿叫"action item"。**挑一个，全文统一。** 不一致会让它在解析你的规则时犹豫。

### 三、越改越长

每次出问题就往里加一条规矩，半年后正文变成三十条。**加规矩的同时要删规矩**——定期回头看，从来没生效过的、和别的重复的，删掉。

<div class="ab-do">

**每季度花二十分钟做一次体检**：

1. 跑一遍三个测试用例，看还过不过；
2. 把正文从头读一遍，删掉从没起过作用的规矩；
3. 检查有没有过期内容（旧模板、旧流程、旧的人名）；
4. 术语扫一遍，统一。

比"等到有人抱怨了再改"省事得多。

</div>

## 在团队里怎么活下来

**一、放到能被 review 的地方。** 跟代码放一起、或者放团队共享盘里。**微信发一段文字过去，三个月后就是四个版本。**

**二、写清楚"谁负责"。** 每个 Skill 指定一个 owner。没有 owner 的 Skill 一定会烂。

**三、改动要有记录。** 至少在文件末尾留一行"最近改了什么、为什么"。半年后你自己也想不起来某条奇怪的规矩是为了防什么。

**四、装之前先看一眼。** 这一条是安全提醒：

::: warning Skill 是可以指挥 AI 行动的
一个 Skill 里的文字，就是给 AI 的指令。**来路不明的 Skill，可能让 AI 做出你没预期的事**——尤其是当 AI 手上有文件读写、命令执行、外部连接这些能力的时候。

所以：**只用你自己写的，或者来源可信的。** 从网上拿来的 Skill，装之前把里面所有文件（包括附件和脚本）从头读一遍，看有没有跟它宣称的用途对不上的操作——比如一个"整理纪要"的 Skill 里出现了往外发数据的步骤。

把它当成"在自己电脑上装一个软件"来对待，而不是"复制一段文本"。
:::
