# 10 · 什么时候该升级成 Agent

<div class="ab-def">

**Agent** 和 Workflow 的唯一区别是：**谁来决定走几步**。你把步骤定死是 Workflow，它自己拆步骤是 Agent。这一章讲什么时候该把这个决定权交出去——以及为什么大多数时候不该。

</div>

## 先把这件事说清楚

Agent 不是 Workflow 的"高级版"。它们是两种不同的东西，各有各的代价：

| | Workflow | Agent |
| --- | --- | --- |
| 你付出的 | 事先想清楚步骤 | 事先想清楚**目标和边界** |
| 你得到的 | 每次一样，可预估 | 能处理你没预想到的情况 |
| 你失去的 | 灵活性 | **可预测性、可调试性、成本上限** |
| 出错时 | 知道错在第几步 | 从头翻它的过程 |
| 变好的方式 | 改那一步 | 改目标描述，然后再看看 |

**把一件确定的事交给 Agent，是拿三样东西换一样你不需要的东西。**

## 什么时候确实该用 Agent

三个信号，要同时满足两个以上才考虑：

### 信号 1：步骤数事先不知道

不是"步骤多"，是"**不知道有几步**"。

```text
❌ "整理纪要 → 抽待办 → 分组 → 发消息"      四步，写得出来
✅ "把这个 bug 查出来"                       可能查三步，可能查三十步
✅ "找齐这五家竞品的定价信息"                 有的官网有，有的要翻到第三层
```

判断方法就是 [01 章](./01-what-is-workflow)那个：**拿张纸写下来。写得出来就不需要 Agent。**

### 信号 2：下一步取决于上一步的结果，而且分支多到列不完

两三个分支，写成 Workflow 的判断节点就行（[01 章](./01-what-is-workflow)）。

但如果每一步的结果都可能开出好几条新路，路径组合起来有几十上百种——那就不是分支，是探索。**探索才是 Agent 的主场。**

### 信号 3：过程本身不重要，只有结果要验收

如果你不在乎它怎么做到的，只在乎最后交出来的东西对不对、而且**对不对你一眼能验**——那让它自己折腾是划算的。

反过来，如果过程需要留痕、需要合规、需要出了事能复盘——**那你需要固定步骤**。

::: warning 三个信号里，第一个是硬门槛
后两个是加分项。**如果你能把步骤写下来，就不该用 Agent**，无论后两条多符合。
:::

## 更常见的答案：局部用 Agent

真实情况通常不是"整条线要不要换成 Agent"，而是——

> **十步里有九步是固定的，只有一步需要探索。**

那就别把整条线交出去。**在那一步里放一个 Agent，外面还是 Workflow：**

```text
① 读需求文档        ← 固定
② 拆成待验证的问题  ← 固定
③ 【逐个去查证】     ← 这一步不知道要查几轮 → Agent
④ 汇总成报告        ← 固定
⑤ 人工确认          ← 固定
```

这样你保住了：**可预测的成本**（只有第三步不可控，而且你能给它设上限）、**可定位的错误**（前后都是固定步骤）、**可验收的中间产物**（第三步的产出仍然要过[闸](./05-checkpoints)）。

<div class="ab-do">

**这是这一章最实用的一句话：Agent 是流水线里的一个节点，不是流水线的替代品。**

下次有人说"这个我们上个 Agent 吧"，先问一句：**是整件事都不确定，还是只有其中一步不确定？**

九成的情况是后者。

</div>

## 前面九章的东西，一条都不能扔

如果你确实要在某处用 Agent，会发现这一篇的东西全都还在用：

| 这一篇讲的 | 在 Agent 里变成 |
| --- | --- |
| [拆步骤](./03-decompose) | 你不拆了，但你得说清楚**目标和完成的标准** |
| [中间产物可查](./04-handoff) | 要求它把每一步的依据留下来，否则你没法复盘 |
| [每步验收](./05-checkpoints) | 变成对**最终产物**和**关键中间态**的验收 |
| [重试与兜底](./06-failures) | 变成**步数上限、成本上限、超时**——不设它会自己兜圈 |
| [人在环上](./07-human-in-the-loop) | **更重要**了。它自主性越高，出口那道闸越不能撤 |

尤其是**上限**这一条：Workflow 的成本是你算得出来的，Agent 的成本是它自己决定的。**不设上限就是把账单交给它。**

## 一个务实的路线

```text
1. 先手动做一遍，把步骤写下来
2. 每一步单独调稳（提示词篇）
3. 高频的步骤打包成 Skill（Skill 篇）
4. 串成 Workflow，设闸、设人工卡点（这一篇）
5. 跑一段时间，看哪一步老是卡住、老是需要人临场判断
6. ↑ 那一步，才是可能需要 Agent 的地方
```

**第 5 步不能跳。** 你跑之前以为需要智能的地方，和实际需要智能的地方，往往不是同一处——多数时候实际卡住的是数据不全、口径不清这类问题，那些不是 Agent 能解决的。

## 这一篇的收口

十章可以压成三句：

> **能把步骤写下来，就写下来。** 确定的事别交给不确定的做法。
>
> **每一步都要能单独验收。** 看不出对错的中间产物，等于没有中间产物。
>
> **Agent 是流水线里的一个节点，不是流水线的替代品。**

## 然后呢

你现在走完了四步：

| | 你会了什么 |
| --- | --- |
| [入门篇](../start/) | 它是什么、为什么会忘会编、怎么把一件事说清楚 |
| [提示词篇](../prompt/) | 让一条提示词稳定、可验收、能交接 |
| [Skill 篇](../skill/) | 把跑通的一步打包，一次写好、反复触发 |
| **Workflow 篇** | 把几步串成能重复跑、每步能验收、错了知道停在哪的流水线 |

下一篇是 [Agent 篇](../agent/)——写不出步骤的那一步，怎么给它目标、怎么划边界、怎么设上限、怎么验收一个自己跑完的东西。MCP 也在那一篇里（[04 章](../agent/04-mcp)）。

不过按老规矩：**先挑一件真实的多步活，照 [08 章](./08-hands-on)手动串一遍，用两周。**

那两周你会发现，你以为需要 Agent 的地方，多数只是需要把某一步的提示词写清楚。
